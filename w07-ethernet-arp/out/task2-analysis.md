# Task 2 실측 결과 분석

현재 Wi-Fi에서 ARP 캐시를 비우고 게이트웨이 ping과 고려대 웹사이트 접속을 실행했다. 캡처 필터는 `arp`, 캡처 시간 제한은 60초로 설정했다.

| 항목 | 실측 결과 |
|---|---|
| 내 PC | 192.168.219.178 / 8c:17:59:ac:3b:cc |
| 게이트웨이 | 192.168.219.1 / 80:ca:4b:1c:3a:2d |
| Wi-Fi 동적 ARP 항목 | 삭제 전 2개 → 실험 후 1개 |
| 게이트웨이 ping | 3회 전송, 3회 응답, 손실 0%, 평균 4ms |
| 웹 접속 | HTTP 200, 원격 IP 163.152.6.10 |
| 60초 캡처의 ARP 패킷 수 | 139개 |

## 먼저 돌아온 항목

삭제 직후 저장한 테이블에는 게이트웨이만 동적 항목으로 나타났다. 캡처에서도 내 PC가 게이트웨이 IP를 묻고 공유기가 응답한 쌍이 확인된다. 외부 네트워크로 보낼 프레임은 우선 게이트웨이로 보내야 하므로 그 MAC 주소가 필요하다. 단, ping 실행 전 이미 항목이 복원되어 있었으므로 수동 ping이 최초 요청을 만들었다고 단정할 수는 없다. 백그라운드 통신도 복원을 일으킬 수 있다.

## 항목 수가 줄어든 이유

Wi-Fi의 동적 항목은 게이트웨이와 192.168.219.189의 2개였으나, 삭제 후에는 게이트웨이 1개만 남았다. 이번 실험에서 .189와의 통신을 다시 수행하지 않아 해당 매핑이 재학습되지 않은 것으로 해석할 수 있다. VMware 가상 어댑터와 static으로 표시된 멀티캐스트·브로드캐스트 항목은 이 비교에서 제외했다.

## 웹 서버가 테이블에 없는 이유

웹 서버 163.152.6.10과의 접속은 성공했지만 ARP 테이블에는 그 주소가 없다. ARP는 현재 링크에서 다음 홉의 IPv4 주소에 대응하는 MAC 주소를 찾는다. 원격 서버의 IP를 목적지로 둔 패킷도 로컬 링크의 프레임 목적지는 게이트웨이 MAC이므로 서버 MAC을 직접 알아낼 필요가 없다.

## 요청과 응답

캡처 기준 1.0514449초에 내 PC가 `192.168.219.1`을 묻는 요청을 보냈다. 목적지 MAC은 `ff:ff:ff:ff:ff:ff`로 같은 브로드캐스트 도메인에 전달되는 주소다. 1.0546687초에 게이트웨이가 응답했고 목적지는 내 PC의 `8c:17:59:ac:3b:cc`였다. 이 응답은 요청한 PC로 보내는 유니캐스트이며 두 프레임 간 간격은 약 3.224ms다.

## 1분 트래픽과 규모 추정

60초로 설정한 캡처에 ARP 프레임 139개가 기록됐다. 첫 패킷과 마지막 패킷의 시간 차는 약 58.995초로, 패킷이 없는 구간까지 포함한 캡처 제한 시간과는 다르다. 이 수에는 내 요청·응답 외에 공유기가 다른 IP를 찾는 브로드캐스트도 포함된다.

컴퓨터 수를 1,000대로 가정하면 과제의 단순 곱셈은 139 × 1,000 = 139,000개/분이다. 다만 이 관측치는 한 PC가 생성한 양이 아니라 그 PC에 보인 트래픽이다. 여러 PC가 같은 브로드캐스트를 중복 관측하므로 이를 실제 네트워크 전체 발생량으로 단정할 수 없으며, 장치별 트래픽과 VLAN 구성에 따라서도 달라진다.

## 검사

최초 검사에서는 tshark가 PATH에 없어 캡처 내용 검사를 건너뛰었다. 이후 Wireshark 설치 경로를 해당 검사 프로세스의 PATH에 추가해 다시 실행했다. 최종 결과는 `4 passed, 0 failed, 0 skipped`이며, opcode 1 요청과 opcode 2 응답이 모두 확인됐다.

## 공개 제출용 캡처

원본은 60초간 관측된 ARP 프레임 139개이며, 공개 저장소의 `arp.pcapng`에는 내 PC의 IP가 ARP 송신자 또는 대상인 프레임만 남겼다. 다른 장치에 대한 요청을 제외한 제출본에는 대응하는 요청·응답 4개(2쌍)가 있다. 따라서 제출본의 패킷 수 4개와 전체 관측값 139개는 서로 다른 범위의 수치다. 원본은 로컬에 보관하며 1분 측정 결과는 `arp-minute-summary.txt`에 별도로 기록했다.
